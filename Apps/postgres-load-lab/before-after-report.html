Before and after

The company-list endpoint was scanning and sorting the full table for every request. A matching index changed the execution plan, reduced buffer work, and cut measured query execution time.

Local validation dataset: approximately 27,000 company rows. Measurements use EXPLAIN (ANALYZE, BUFFERS) against the same PostgreSQL dataset.

What changed in between

Indexes were aligned with the list queries

The list endpoints use ORDER BY created_at DESC. Migration 002_list_order_indexes.sql adds indexes in that same order for all three resources:

CREATE INDEX IF NOT EXISTS companies_created_at_idx
  ON companies (created_at DESC);

CREATE INDEX IF NOT EXISTS users_created_at_idx
  ON users (created_at DESC);

CREATE INDEX IF NOT EXISTS inventory_created_at_idx
  ON inventory (created_at DESC);

These values prove the plan improvement for this dataset and cache state. They are not universal performance promises. Server-level validation should still compare application p95/p99, throughput, errors, CPU, storage I/O, and connection-pool utilization under an identical workload.

Why it matters under load

  • The old plan performed work proportional to the growing table before returning only 50 rows.
  • The new plan can stop after reading the requested entries, keeping list latency more stable as data grows.
  • The tradeoff is additional index storage and a small amount of maintenance work on inserts and deletes.
  • Deep OFFSET pagination can still become expensive; keyset pagination is the next optimization if measurements identify it as a bottleneck.
